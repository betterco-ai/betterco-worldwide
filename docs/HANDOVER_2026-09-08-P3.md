## 2. The deploy ask (for the next environment)

**⚠️ This deploy breaks the ordering UI.** The case list no longer returns `caseCommonId` (it
returns `caseId`), so a frontend reading that field gets `undefined` and its case links go dead.
A compatibility shim would not help — the *list shape* changed, not just the id format. The API is
fine to exercise with curl; the web UI needs a matching change from whoever owns it. Decide that
before deploying, because dev is the only interactive test path we have.

```
git fetch origin
git checkout p3/contract-cutover      # 75019e924
<usual build>
restart
```

**Startup is the unproven part.** 922 tests pass locally but nothing has ever started this wiring:
`CaseContractService` sits between the controller, the gateway and the acquisition store. The
dependency graph is acyclic (checked), but Spring wiring is exactly what compiles and then refuses
to start.

**Check startup POSITIVELY. The obvious negative grep is not diagnostic:**

```
grep -c "Started Application in" <log>     # expect 1
```

`UnsatisfiedDependencyException` matches *any* bean failure, most of which have nothing to do with
this change - and this was not hypothetical. On 8 September the first restart failed on
`authenticationService` because `application-development.properties:52` is
`spring.cloud.azure.credential.username=${AZURE_USER_USERNAME}` with **no default**, so an unset
env var left the placeholder literal and Azure tried to authenticate against a realm called
`${AZURE_USER_USERNAME}`. At grep level that is indistinguishable from a real bean cycle.

Launch with the vars explicitly empty:

```
export AZURE_CLIENT_ID= AZURE_USER_USERNAME= AZURE_USER_PASSWORD=
```

Only if startup has actually failed is the negative grep useful, and then read the *bean name* in
the exception rather than the exception type.

Then four checks (`BASE`, `WS` and auth as in `betterco-backend/docs/TESTING_READY_FLAG_FIX.md`):

```bash
# 1. the list hands out OUR ids and OUR vocabulary
curl -s "$BASE/restapi/v1/workspaces/$WS/document-search/cases" | head -c 400
#    expect caseId (24-hex) + status; expect NO caseCommonId and NO statusName

# 2. that id addresses the case
curl -s "$BASE/restapi/v1/workspaces/$WS/document-search/cases/<caseId>"

# 3. documents carry our ids and their roles
curl -s "$BASE/restapi/v1/workspaces/$WS/document-search/cases/<caseId>/documents"
#    expect CS01 with roles ["REGISTERAUSZUG","GESELLSCHAFTERLISTE"], status "stored"

# 4. the vendor's number is no longer a key
curl -s -o /dev/null -w "%{http_code}\n" "$BASE/.../cases/1000005503"     # expect 404
```

**Check 4 is the one that matters.** A 200 there means a vendor id is still a handle and the
cut-over did not happen.

## 4. P3 design decisions — please do not re-litigate these

- **The public case id is `KycCaseLink.id`**, not the source's number and not the matter id. Both
  alternatives are sometimes null (the source assigns its number later; the matter id is absent
  wherever client creation is off, and on case 189). Side effect worth having: a case the source has
  not started now has an identity and a status.
- **Status is derived, not passed through.** Source-ready but documents not held → `building`;
  settled with something missing → `incomplete`. There is a test asserting status never calls the
  source: a consumer polling must not be able to make us spend money.
- **`SourceDocuments` is internal.** The gateway used to fill the generated consumer DTO directly,
  so `availability`, the estimated download date and a `type` that is really a status were part of
  what Septeo saw. That is now an internal record.
- **The neutral id space only holds when ingestion is on.** With the flag off there are no
  acquisitions, so the source's listing passes through (WARN logged). This makes
  `aggregation.ingestion.enabled=true` a **go-live prerequisite**, not an optimisation.
- **Deliberately excluded:** `evidenceLevel` and the per-artefact cost field, both outside the scope
  as restated by the user on 8 September.
