## 2. What P1 does

A document order creates a BetterCo **client with one matter** and files the vendor's case id on it.
Reuses `CustomerService.createCustomer(ws, org, createDefaultCase=true, caseName, actor, CLIENT)`;
the organisation is the workspace's first. All of it behind `document-search.create-client`,
**default off** — with the flag off the order path behaves exactly as before.

Three decisions not in the original plan, all test-pinned:
1. The client is created **before** the billable vendor call — no paid order without a home.
2. **`retryCreate` creates nothing.** It is a second route into `completeCreate` (idempotency
   replay) and reuses the link's existing client.
3. Filing the vendor reference **cannot fail the order** — own try/catch inside `completeCreate`.

**Verification:** 65 aggregation/kyc tests green; full suite 790 tests / 7 failures / 13 errors —
identical to the `dev` baseline, no failure in any touched class.

## 3. Facts discovered that contradict earlier assumptions

- **CI does not verify a branch.** `app-tests.yml` gates its job on
  `github.event.review.state == 'approved'` — a push, and even an open PR, run nothing. Tests run
  only after a human submits an approving review.
- **Verification is local and possible.** No Maven on PATH and no `~/.m2`, but the dependency tree
  resolves from Central with no private repos, so a scratchpad Maven runs the real `mvn -B test`.
  Baseline on clean `dev` is **735 tests / 7 failures / 13 errors** — judge by *no new failures*.
  Use `-Djacoco.skip=true` if the local jacoco agent jar is corrupt.
- **Staging orders were hitting the LIVE vendor.** `application-staging.properties` overrode only
  `create-enabled=true` and inherited `base-url = api.knowyourcustomer.com`. That is what
  `config/staging-kyc-sandbox` fixes.
- **`kyc-com.secret` is a vault secret NAME**, not a credential (`SecretProvider.getSecret(name,
  KycComSecret.class)` → `record(clientId, secret)`). Value must be JSON:
  `{"clientId":"…","secret":"…"}`.
- **Vault topology:** `know-your-customer-com-sandbox` now exists in **`bc-dev-vault-dev`**.
  `betterco-dev` has no kyc secrets at all. `bc-app-vault` and `bc-stg-vault` hold their own.
  The repo's `application-development.properties` points at `betterco-dev`, which is probably stale —
  pin the endpoint with `-Dspring.cloud.azure.keyvault.secret.endpoint=…` rather than trusting it.
- **The sandbox is compatible except for document download.** Token, `/v2/Jurisdictions`,
  `/v2/CompanyTypes`, search, create, status and document *listing* all behave like production.
  Download 404s from the sandbox base and 401s from the host in the returned links. Fine for P1,
  **blocking for P2**, and a vendor question. Sandbox trial **expires 2026-10-19**.

## 4. The blocker

Testing on the dev server is stopped at **Azure credentials**. `application-development.properties`
declares `spring.cloud.azure.credential.{client-id,username,password}` as unresolvable placeholders
(`${AZURE_CLIENT_ID}` etc.), so the app will not start without them, and nobody has produced the
values. Directory lookup found two candidate registrations:

- `betterco-dev` — `583fc344-1c9e-458c-b6a2-49201b6ad38e`
- `betterco-dev-server` — `236f6ed3-1ba0-45bb-a71f-c1a16fe9ccd6` (the identity the dev box already
  runs as)

**Recommended fix, not yet made:** grant `betterco-dev-server` `Key Vault Secrets User` on
`bc-dev-vault-dev`, then delete the three `spring.cloud.azure.credential.*` lines from the
development profile so `DefaultAzureCredential` falls back to the machine's own identity. No
password on the box, nothing to rotate. This was offered and not yet approved.

Dev server preconditions otherwise: Mongo on 27017 ✅, workspace `69d51c7a…` with organisation
`69d51cd4df31370be25de3f4` ✅.

Build with **`mvn clean package -DskipTests`** — `dev`'s own suite is red, so a normal package fails.

## 5. Decisions taken

- **D1 retention — ANSWERED.** Documents kept indefinitely; deleted with the client (a cascade that
  does **not** exist today — `CustomerService.deleteAllClientInfo` orphans documents already);
  reusable across customers while fresh — window on `fetchedAt`, default 7 days, per source.
- **D6 — OPEN.** Whether kyc.com's licence permits serving a document bought for one customer to
  another. Our willingness is not their permission. Never asked.
- **Document types:** kyc.com's per-jurisdiction definitions as the source standard, mapped onto
  BetterCo's **built-in** enum — a custom `documentType` string is invisible to reviewers in the UI.
  The backend has no vendor-neutral vocabulary at all (`KYCDocumentType` is a 7-value German enum);
  building it is P3 and must precede freezing the contract.

## 8. Known flaw in P1, unfixed

Client creation sits inside `acceptCreate`, which runs **after** the `create-enabled` dry-run check.
So with creates disabled the P1 path never executes — P1 cannot be exercised without a real create.
The sandbox makes that free rather than fixing it.
