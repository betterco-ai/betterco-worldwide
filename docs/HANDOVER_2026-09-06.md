## 2. The memo — how risky is it to keep building?

**Blast radius is low; waste risk is climbing. They are different things and only one is rising.**

Nothing built this week is deployed, merged or enabled anywhere. `document-search.create-client` is
true only in `application-development.properties`. A wrong call today cannot reach a customer,
corrupt production data, or spend money. **The worst case is rework on branches nobody has merged.**

What *is* rising: every layer sits on assumptions no running system has tested. F1 is the exception
— its premise was checked against 18 real vendor cases. The vendor-target probe logic, the
split-try in the create path, and the acquisition model have never executed against real data. Four
layers deep, a wrong assumption at the bottom costs four rewrites instead of one. **One deploy
collapses that risk**, and it is exactly what is blocked.

So the next step was chosen by risk, not by plan order:

| Risk | Work | Why |
|---|---|---|
| **Low** | The type-mapping layer; the four ingestion-seam reads the plan insists on | Inert, unit-testable, settles a decision P3 needs anyway |
| **Medium** | Poll policy + give-up point (P2 tasks 3–4) | Touches running code but is fully unit-testable — and #2294 owes it |
| **High** | Ingestion primitive, worker, content endpoint | First code calling platform services and the vendor for real; cannot be proven without a deploy |

**Recommendation: do the low one, hold the high one until one deploy has happened.** Not because it
is hard, but because being wrong there is expensive and invisible.

A second cost worth naming: **four stacked PRs is already a lot to ask of one reviewer**, with a
required merge order and rebases if the first attracts substantive comments. `dev` moved twice on
6 September alone. A fifth branch makes that queue worse, and that cost lands on someone else.

### What each one actually fixes

- **R1** — `ready` meant "the vendor created this", not "the vendor finished it", because
  `caseReadyDatetime` is stamped at creation *on the sandbox*. Every link was born ready, so the
  status poller (which selects not-ready links) never revisited it and the stored status froze
  forever. Includes a Mongock backfill for links already frozen.
- **R2** — every case records which vendor world produced it. A sandbox case id does not exist in
  production; the Hetzner box demonstrates it today, answering `400 "Api Error"` for its one stored
  case. Also retires the polling noise R1 would otherwise create.
- **R3** — a create the vendor **already charged for** could be recorded as `"Create failed"`, the
  one status treated as safe to re-order. The idempotency key meant to prevent double billing was
  causing it. Now only a failure *before* the vendor answers is retryable.
- **R4a** — the acquisition record: lifecycle, entity, repository, service.

## 6. Things that will bite whoever picks this up

- **The bug in R1 only reproduces against the sandbox.** `caseReadyDatetime` is stamped at creation
  there and at completion on production. A production-pointed server showing no difference is the
  **correct** result, not a failed test.
- **An old-code instance on the same Mongo undoes R1 while you watch** — it re-sets `ready` from
  `caseReadyDatetime` on every poll. Stop it, or give the test instance its own database.
- **Staging orders from the LIVE vendor** — measured 5 September, 200 real Companies House rows.
  Every "just test on staging" is a real order at $18–$88.
- **Every sandbox PDF is the same 904-byte stub.** We have never retrieved a real registry document
  through our own stack. That is what the first billable order is for.
- **A custom `documentType` is invisible in the UI** — it round-trips through the API and the
  reviewer can never find it. Worse than not filing it, because it looks filed.
- **CI verifies nothing** before an approving review. Verify locally: Maven 3.9.9 and a populated
  repo live in a session scratchpad, Java 17 is installed. Baseline is **795/7/13 without a Docker
  daemon, 806/7/0 with one** — re-measure against a fresh `dev` rather than trusting either number.
