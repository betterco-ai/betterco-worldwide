STOP Four things that must be true first

None of these is code, and none is yours alone to decide. Opening staging to STP before they clear is the expensive version of this plan.

Infra — costs money if skipped

The staging vault has no sandbox secret

application-staging.properties in this stack already points staging at the KYC.com sandbox. The matching Key Vault entry know-your-customer-com-sandbox does not exist in bc-stg-vault. It resolves lazily, so staging boots clean and then fails every vendor call. Do not "fix" it by pointing staging at the production secret — that turns every STP test order into a real one at $19–$119.

Frontend — breaks the UI

The case list changed shape

P3 returns caseId where the list used to return caseCommonId, and status where it returned statusName. A frontend reading the old field gets undefined and its case links go dead. A compatibility shim does not help — the shape changed, not the format. Whoever owns the ordering UI needs a matching change in the same window.

Commercial — not a deploy

Septeo has not been told

Björn is integrating against the vendor's identifiers now. The note is drafted and unsent. Opening staging is the moment the break becomes real for him, so the note goes out before the invitation, not with it.

Expected behaviour, not a bug

Staging may refuse to start

This stack adds a startup assertion: the app refuses to boot when ordering is armed against the paying vendor outside the production profile. If staging will not come up after the deploy, read that first — it is the guard doing its job, and it means the vendor config is wrong.

GATE 5 Staging, then STP

Only after gates 1 to 4 and all four blockers.

  1. Create know-your-customer-com-sandbox in bc-stg-vault
    JSON, shape {"clientId": "...", "secret": "..."} — the same mechanism as the production credential. Without it every vendor call on staging fails, and the failure appears only at call time.
  2. Deploy and confirm it starts
    If it refuses, check the vendor config before anything else — see blocker 4.
  3. Prove staging is on the sandbox, not the live vendor
    A GB search must return the five sandbox fixtures (CROPWELL BISHOP CREAMERY LIMITED | 00364890 first). If it returns real Companies House rows, stop — staging is on the live vendor and every STP order will be billed.
  4. Re-run the gate 4 checks on staging
    Same list. Staging is the first environment with a vendor config of its own, so the world-dependent ones (o5, o2) can behave differently here than on dev.
  5. Confirm the Septeo note has gone out
    Then send the invitation, with the new contract shape stated in it: caseId, status, our document ids, and the two refusals they will meet.
The one thing staging still cannot prove

Every file the sandbox serves is the same 904-byte stub. STP can exercise the whole contract on staging — ordering, polling, listing, downloading — and still never see a real registry document. Only one billable order against the production vendor settles that, and it settles three other open questions with it. It is not part of this runbook because it needs a decision, not a merge.
