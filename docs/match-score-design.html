Match Score Design

A free call that answers “is this registry entry the company in your record?” before the caller spends money on a case — returning every candidate it considered, with the rule that ranked them published and versioned.

01 The problem

Septeo do not want to open a case when the company in front of them might not be the company in the registry. A case is billable; a wrong one is money spent on the wrong entity, and in a compliance file it is worse than money.

The score they saw exists only as a hand-built column in our September simulation. Nothing in the API produces it.

They offered two ways to close that. The chosen one puts the score in front of the caller and leaves the decision with them. The alternative — a minimum score enforced inside our create — was declined on purpose: it refuses orders silently, and it moves a rule the caller owns into our release cycle.

02 Two endpoints, both free

Creating a case remains the only billable action in this API.

      "rawname": "Sur la Pree B.V.", "externalCode": "54406951",
      "signals": { "numberMatches": false, "nameMatch": "EQUAL" } }
  ] }

Each candidate carries its own score, band and signals. The top-level score is the best of them under the published selection rule — stated in the response, not only in documentation, because a ranking nobody can see is the same problem as a score nobody can audit.

A conflict governs — a correction found while implementing

Revision 2 first published “highest band wins”. Writing the scorer showed that wrong: in the Sur la Pree case the candidates are Barcarolle at 70 and the real Sur la Pree at 85, so the highest band reports 85 — a reassuring score for exactly the record whose number points at somebody else, burying the finding this feature exists for.

A NUMBER_AND_NAME_CONFLICT therefore outranks everything else, and the rules file states that and its reason. The same ordering sorts the candidate list, so the order a caller reads is the ranking that chose the score.

No address, no legal form in the request. Every extra input is another rule we have to publish, and no band below needs them.

Candidate fields reuse KycSearchResult exactly, so a caller who consumes cases/search needs no new model. candidates is an empty array when nothing was found, and every signals field is present on every response — inapplicable ones null rather than omitted, so nobody has to tell false from absent.

03 Two lookups, then arithmetic

What revision 1 got wrong

Revision 1 performed one lookup, by name, and compared the caller’s number against the hits. Replay Sur la Pree through that: a name search for “Sur la Pree B.V.” returns the real Sur la Pree, never Barcarolle Holding B.V. The number pointing at a different company is never seen and the row scores 85 — the finding that motivated the whole feature is the one it would miss.

The number has to be resolved independently of the name, which is what the simulation did by hand: “gesucht haben wir mit eurer Registernummer bzw. mit mehreren Namensvarianten”.

  1. Look up by number, when one is supplied and the jurisdiction’s id scheme is comparable. Answers “whose company is this number?”
  2. Look up by name, always. Answers “is there a company by this name?”
  3. Merge and de-duplicate on externalCode; a company found by both is marked foundBy: NUMBER.
  4. Score every candidate against the published band table, then rank by the published selection rule.

Both lookups use the existing free vendor search. Two searches roughly double the latency of one; both are free, and the caller is about to spend money, so the trade is worth stating and not worth agonising over. signals.lookups records which ran, so a caller can see whether the number was resolved at all.

Why no new vendor capability is needed

externalCode is the registry id: the contract documents enrichment.registryId as “the company’s registry id (same value as externalCode)”, with a decoder covering CRN, CIN, OGRN, USCC and UEN. So numberMatches is a comparison against data the lookups already returned.

The bands

Scored per candidate; the response’s top-level score is the best of them.

NUMBER_AND_NAME This candidate’s externalCode equals the number and its name equals theirs.

NUMBER_RESOLVES_SCRIPT_DIFFERS Number matches, names differ, and the two names are in different scripts. The Bulgarian rows: same company, written in Cyrillic.

NUMBER_AND_NAME_CONFLICT The number resolves to this company and the name resolves to a different one. Two lookups, two companies — the Sur la Pree case, and the strongest evidence of a wrong number.

Two ids share the score 70, deliberately

The score is what a threshold compares against, and Septeo have already seen these six numbers. The id is what tells them which kind of doubt they are looking at.

This also demotes the script rule. In revision 1 it carried the whole 95/70 split; with the number resolved independently the conflict identifies itself, and script now only separates 95 from 70 when there is no competing name candidate — different scripts mean the names cannot be compared and the number is authoritative, the same script and a different name mean the number points elsewhere. Still no similarity metric, still no transliteration table to publish.

Name normalisation, published with the rules

Applied to both sides, in order. There is deliberately no fuzzy score: a continuous 0–100 invites a threshold nobody can reason about, whereas a band can be argued about in words.

  1. Trim, collapse internal whitespace to single spaces.
  2. Uppercase with Locale.ROOT.
  3. Remove diacritics (NFD, drop combining marks).
  4. Drop . , ' " ( ) - and substitute & → AND.
  5. Strip one trailing legal-form token from the published per-jurisdiction list — B.V., GMBH, LIMITED, S.L., S.À R.L. — and only at the end.

04 Transparency as a property of the code

The band table, the legal-form tokens and the non-company-register patterns live in one versioned file, src/main/resources/kyc/match-rules.json.

  • MatchScoringService reads it.
  • GET …/match/rules serves it verbatim.
  • A test fails if those two are ever not the same resource.
  • Every scored response carries the rulesVersion that produced it, and a test pins the current value so a rule change cannot ship without bumping it.

The trap this closes: a caller sets a threshold at 85, we later change how a band is computed, and their threshold silently means something different with nothing failing visibly. With the rules published and stamped, that change is diffable instead of invisible.

05 Three answers, not one

A caller needs three separate things before spending money. One call returns all three.

Preconditions — to be confirmed, with defined fallbacks

Three assumptions this design rests on, none yet measured. Each has defined behaviour if it fails, so none is a TODO.

08 Cut, and why

CutReason
Per-partner configurable rules, and a minimum-score gate inside createBoth were asked for. Published, versioned rules plus the caller’s own threshold cover the need — and a threshold inside our create refuses orders silently, which is the failure this design exists to avoid.
Address and postcode signalsMore inputs, more published rules, no band that needs them.
Fuzzy similarity scoringBands are arguable in words; a percentage is not.
More than two lookups — name variants, which the simulation used by handIt would raise recall on band 85 and is a defensible later addition, but each variant is another published rule and another call.
TransliterationThe script rule in §03 makes it unnecessary.

09 Still open

  • The three preconditions in §05 — the first of which decides whether this is a 1 October change at all.
  • Septeo’s threshold, and whether they adopt the bands as published. Asked in the 17 September draft; not in the version sent on the 18th. Not a blocker — they set their own threshold against published rules — but worth one line when the call happens next week.
  • Recall on band 85 is inherited from the vendor’s own name matching. Where only a name lookup is possible, what we get to evaluate is what they chose to return.
