Aggregator Roadmap

Programme design · phases 1 to 4

From passthrough to aggregator

The BetterCo platform is the reference system. It calls an aggregator, the aggregator routes to a source, and the document lands in a BetterCo client. Today none of that is true for document search. Here is what gets built, in what order, and what fits before 1 October.

00 Overview

Phases 1 and 2 make sources interchangeable. Phase 3 makes the choice between them intelligent. That distinction is why phase 3 is real work rather than a wish-list — and also why it can wait until after the go-live.

Phase 1merged & live on dev

The aggregator exists

The platform owns the case and kyc.com is the only source. Merged and running on dev, where an order now produces a client with one matter. Storage is P2.

Phase 2after 1 Oct

A second source

A source port, a routing table, then France via INPI and Britain via Companies House — both already built. Cut from the go-live on 5 September: margin, not the promise.

Phase 3later

The decision layer

Evidence levels, least-cost routing, reuse of stock. The aggregator decides instead of looking up.

Phase 4later

Housekeeping

Webhooks replace polling, the kyc.com Java exception retires, ordering moves into the app UI.

Throughout: exists today to build open decision

01 Why

Measured in betterco-backend on 28 August 2026 — three findings, each checkable in the code:

  • The order never reaches a client. KycCaseLink, the record a document order creates, holds workspaceId, customerId, kycCaseCommonId, jurisdiction, companyName, statusName, ready, idempotencyKey — and no businessRelationId, no reference to domain/Case.
  • Nothing is stored. Every read is a live vendor call: getCaseStatusById → client.getCompany(…), listDocumentsById → client.getCompanyDocuments(…), download → client.downloadDocument(…). No stock to reuse, no per-case cost record.
  • The consumer's handle is the vendor's identifier. extractCaseCommonId() reads kyc.com's caseCommonId and it becomes the path parameter in /cases/{case_common_id}. No second source can mint that number.

02 Phase 1 — the aggregator

In scope. The aggregator exists, kyc.com is its only source, and a document order produces a BetterCo client with one matter whose documents are stored by us.

Not in scope. Replacing the kyc.com Java client with the python route; changing search, jurisdictions, coverage, company-types or legal-forms; the customer-facing UI.

Domain model

The aggregate already exists. domain/Case carries businessRelationId (the client), workspaceId, status, caseAML, caseOrigin and externalIdentifiers. A BetterCo client with one matter is the case; kyc.com's case maps onto it one-to-one.

The contract STP sees

Unchanged: search, jurisdictions, coverage, company-types, legal-forms. The break is confined to cases and documents.

kind is the vendor-neutral document kind from our curation, not the vendor's label. ready means nothing more is coming — every requested kind has reached a terminal state — not everything was found. includePending is accepted and ignored for one release so STP does not change its calls twice.

Migration for STP

The case id changes from Long (kyc.com's) to an opaque String (ours). Agreed to break now, while Björn Hartenstein is still integrating, rather than after his polling loop ships — the whole point of step 1 is that STP migrates once.

The two fixes that rode along are live too. The vendor’s document path is case-sensitive — /v2/documents/{id} returns 404, /v2/Documents/{id} returns the bytes, and our client used to send lowercase; every document now downloads from dev. And document type is derived from the vendor’s name minus its trailing date, so the case returns Annual Return and Certificate of Change of Name where category says only “Other Company Documents”.

Ordering was checked against the sandbox immediately before the order: five fixtures with CROPWELL BISHOP CREAMERY LIMITED | 00364890 first. Real Companies House data there would mean production, and the test aborts.

Ingestion and cost

Documents arrive progressively, long before the case is ready, so ingestion is driven per document and never by case-ready. Backoff is a per-source policy object — a synchronous source declares no polling at all. The kyc.com schedule is now 1m, 5m, 15m, 1h, 6h, 12h, 24h, dense at the front because the spread is enormous: a sandbox case was ready 40 seconds after the order, while production case 189 was still building after four and a half hours. An earlier version started at one hour, which left the platform reporting “Initializing Case” for 52 minutes after the vendor had finished. This replaces today’s flat five-minute scheduler.

A case may draw documents from several sources at once, so cost lives in charge records, not on the case:

Charging modelUnitEffect on a case
PER_CASE — kyc.comone per (case, source)first acquisition charges; the other nine documents are free
PER_DOCUMENT — sidecar sourcesone per acquisitioneach document charges
future models—new strategy, no schema change

This mirrors the existing BillingComputationStrategy pattern rather than inventing a second mechanism. Vendor cost and customer billing stay separate meters: document orders get their own CaseOrigin value, so the billing rule can be decided later without a migration.

03 Phase 2 — a second source

What it adds

  • A SourceAdapter port, extracted from two working implementations rather than guessed — the kyc.com Java client and the FastAPI sidecar. Operations: search, availableDocuments, retrieve, pollAcquisition.
  • A routing table: (jurisdiction, document kind) → ordered list of sources. Static and deterministic here; phase 3 is what turns lookup into decision.
  • A sidecar transport adapter — HTTP over loopback to 127.0.0.1:8090, shared-secret auth, the contract already briefed in api/INTEGRATION.md.
  • Per-source policy for the newcomers: charging PER_DOCUMENT, backoff none for synchronous sources such as INPI.

Phase 1's domain model does not change. A second source adds rows to a table and one adapter — it does not touch the case, the acquisition, or the contract STP sees. That is the test of whether phase 1 was designed correctly.

Which source is second — measured, not assumed

One case in each market, measured on staging on 29 August:

France is source two, Britain third. France is the most expensive market we buy — five times Britain or Denmark — and sits first on Septeo’s priority list. Britain follows immediately because it is the same shape and its route already downloads filing PDFs; the only difference is that the saving is $18 rather than $88.

A correction to yesterday's spec

The phase-1 document put Germany first. Two facts say otherwise. Measured prices make France the larger saving by a factor of five — and Björn's opening mail states the requirement plainly: "we would like to find and download registration documents for companies outside of Germany." Germany matters for our own product, not for this go-live.

Policy leak worth naming

Germany is in kyc.com's list at $18, so after phase 1 the aggregator would happily buy German documents from kyc.com — against the standing rule that we source Germany ourselves. Until the routing table exists, that rule is remembered rather than enforced. The table is the fix.

Sequence within phase 2

  1. Extract the port; kyc.com becomes adapter one with no behaviour change — the phase-1 tests prove it.
  2. Add the routing table with a single rule: everything → kyc.com. Still no behaviour change.
  3. Add the sidecar adapter and France via INPI; route French document kinds there, everything else unchanged.
  4. Britain via Companies House — same shape, already downloads PDFs.
  5. Afterwards: Germany once the sidecar drift (D4) is resolved, and Denmark only if a data-only source belongs in a document aggregator at all.

04 Phases 3 and 4

Phase 3 — the decision layer

Phases 1 and 2 leave a static table. Phase 3 replaces the lookup with a decision, and it is where the aggregation thesis actually pays:

  • Evidence levels — data / document / certified. A Datainfogreffe statement is not a Kbis substitute; without the level, "cheapest source" is a meaningless instruction.
  • Least-cost routing — the cheapest source that meets the required evidence level, aware that kyc.com charges per case while an INPI acte is a bundle.
  • Reuse of stock — do not fetch what we already hold fresh. Needs a freshness policy and both clocks. Resolved 9–11 September. Both clocks now exist: contentDate is written where the vendor inlines a filing date, and the freshness window is built as a per-source policy, off by default. What is not built is reuse across customers, and that is blocked on something the record does not carry: an identity for the company that survives across clients. Vendor document ids repeat across cases and mean different things, and jurisdiction plus company name is not an identity. That key is the open item, not the window.
  • Per-case cost reporting — Resolved 9 September. The meter is instrumented: every order records amount, currency, band and chargedAt. The number is labelled a list price (LIST_PRICE_CONFIGURED), never an invoiced one, and a sandbox order records NOT_BILLABLE rather than a price it never cost.

Not required for 1 October. A static routing table is correct, just not clever.

Vendor guidance that changes P3

KYC.com (Latika Puri, 23 July): “the document name (excluding the date suffix) is the more reliable field for identifying document types. The category field is currently not normalized across jurisdictions and should not be considered a canonical document type.”

So the document-kind vocabulary P3 has to build should key off name minus its trailing date, with category kept only as a fallback for an unnamed document — not the other way round. That is already how test/p1-on-dev derives it.

Phase 4 — housekeeping

Named separately so it does not quietly attach itself to the deadline: replace polling with the kyc.com v2 webhooks (CaseReady, DocumentUploaded — the backend has no webhook endpoint today); retire the kyc.com Java exception so every source reaches the aggregator through one shape; move ordering into the app UI, since today only STP and our internal tool can order.

The scope cut — 5 September

France and Britain are out of the 1 October go-live. The 29 August plan carried all six phases inside the deadline. Why ownership comes before the contract

An opaque caseId only means something once a Case owns it — ship it earlier and it is an alias table over kyc.com’s number, with a real chance the shape changes again once ownership lands. Derived status has the same dependency: it is computed from acquisitions, which arrive in P2. Building the substance first buys one contract break instead of two.

Telling Björn is decoupled from shipping it. The migration note goes out immediately — a message, not a deploy — so he holds his polling loop while we build, and the cut-over lands at P3.

Where the code lives

The com.betterco.app.aggregation package exists from P1: ownership and ingestion are written there rather than in integration/kyc_com and moved later. With a single source there is nothing to route, so the aggregator only becomes a router at P5 — which makes P5 an addition rather than a refactor.

How we know it works — corrected 30 August

app-tests.yml runs its job only when github.event.review.state == 'approved', so a branch push verifies nothing and neither does an open pull request. Tests run only after a human submits an approving review. Earlier versions of this page said CI was the gate before review; it is not.

Verification is local instead: the dependency tree resolves from Central with no private repositories, so a scratchpad Maven runs the real mvn -B test without touching the repo. The baseline matters — clean origin/dev is 735 tests, 7 failures, 13 errors — so a branch is judged by no new failures, never by a green suite.

What actually sets the pace

  1. The backend dev’s review and release train. We branch and push; they review, merge to dev, and it reaches staging on their cadence. Six phases, six round-trips.
  2. Septeo’s own migration. P3 changes Long to String in Björn’s client, though he is told at P1. That is his work on his calendar, and nothing after P3 validates end-to-end until it is done.
  3. The retention decision (D1). Storing documents forces it, and no amount of code answers it.

Scope for 1 October

The six MVP items above — not all six phases. France, Britain, the routing table and the cost records follow the go-live. What stays out beyond that is not effort but unknowns: Germany until the sidecar drift is resolved, Denmark until we decide whether a data-only source belongs in a document aggregator at all.

The saving those sources represent is real — $88 on a French case, $18 on a British one — but it is margin. The promise is that a document ordered through BetterCo lands in a BetterCo client file and stays there, and that is what the six items buy.

D1 answered — 29 August

Documents are kept indefinitely and die only with their client, so there is no retention job to build — deleteClient gains a cascade instead. A document may be reused for another customer while it is fresh: the window applies to fetchedAt, defaults to seven days, and is configurable per source. Where a source offers a free freshness check (INPI, Companies House), prefer asking whether anything changed over trusting the clock.

This unblocks P2 for production. It does not settle D6: our willingness to reuse a document is not the same as the vendor’s permission to, and kyc.com’s licence terms have not been asked.

The honest summary

The connectors are built. France, Britain and Germany all have working document routes, and the Java side reuses the case, the storage and the billing strategy that already exist. The remaining build is small.

What is not small is the coordination: six pull requests through the backend dev’s release train, one client change only Septeo can make, and one retention decision only a person can make. Those are the schedule — so the migration note goes out immediately and both gates open alongside the build rather than after it.
